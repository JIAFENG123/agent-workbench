## 二、一次运行到底发生了什么

```
浏览器                 FastAPI                    Postgres          NVIDIA NIM
  │                       │                          │                  │
  │ POST /api/runs        │                          │                  │
  ├──────────────────────>│  建 Run 行(status=queued) │                  │
  │                       ├─────────────────────────>│                  │
  │  202 {run_id}         │                          │                  │
  │<──────────────────────┤                          │                  │
  │                       │                          │                  │
  │                       │ asyncio.create_task ─┐   │                  │
  │                       │  (不阻塞这次请求)     │   │                  │
  │                       │<─────────────────────┘   │                  │
  │ GET /{id}/stream      │                          │                  │
  ├──────────────────────>│                          │                  │
  │                       │ 先重放已持久化的事件       │                  │
  │  SSE: run_started     │<─────────────────────────┤                  │
  │<──────────────────────┤                          │                  │
  │                       │                          │                  │
  │                       │  ReAct 第 1 轮: 带 tools 的对话请求            │
  │                       ├──────────────────────────┼─────────────────>│
  │  SSE: step(start)     │                          │                  │
  │<──────────────────────┤                          │                  │
  │  SSE: token × N       │  流式增量回传             │                  │
  │<──────────────────────┤<─────────────────────────┼──────────────────┤
  │  SSE: tool_calls      │                          │                  │
  │<──────────────────────┤                          │                  │
  │                       │  执行 kb_search           │                  │
  │  SSE: tool_call       │  ├─ 查询改写 ─────────────┼─────────────────>│
  │<──────────────────────┤  ├─ 嵌入查询 ─────────────┼─────────────────>│
  │                       │  ├─ 向量检索 + BM25 ──────>│                  │
  │                       │  ├─ RRF 融合               │                  │
  │                       │  └─ 交叉编码器重排 ────────┼─────────────────>│
  │  SSE: tool_result     │                          │                  │
  │<──────────────────────┤                          │                  │
  │                       │  第 2 轮: 带工具结果再问模型                    │
  │                       ├──────────────────────────┼─────────────────>│
  │  SSE: token × N       │                          │                  │
  │<──────────────────────┤                          │                  │
  │  SSE: citations       │  更新 Run(status=…)       │                  │
  │  SSE: usage           ├─────────────────────────>│                  │
  │  SSE: run_finished    │  写 usage_ledger          │                  │
  │<──────────────────────┤                          │                  │
  │  连接关闭              │                          │                  │
```

几个要点：

**为什么 POST /api/runs 立刻返回 202。** Agent 一轮跑几十秒到几分钟。如果把整个执行塞在请求里，会撞上 Render 的请求超时，浏览器也会以为卡死了。所以创建和订阅是分开的两个动作。

**为什么事件要先落库再广播。** 订阅者可能在运行开始之后才连上来（前端是先 POST 再开流，中间有几百毫秒）。只做内存广播的话这段空窗期的事件就丢了。落库 + `seq` 递增 + 客户端带 `Last-Event-ID` 重连，三者合起来才是完整的重放语义。

**token 事件不落库。** 它是唯一高频事件（一次回答几百上千条），一条一行会把免费层的数据库写爆，而且重放时也没人想看逐字过程。代价是断线重连后已输出的文字不会补回来——这个取舍写在了 `PERSISTED_EVENT_TYPES` 的注释里。

## 三、检索链路

```
用户问题
   │
   ├─ 1. 查询改写（LLM，可关）         → 原句 + 3 个变体
   │
   ├─ 2. 每个变体各走两路检索
   │      ├─ 向量检索：pgvector HNSW，cosine 距离，取 top-20
   │      └─ BM25：进程内 rank_bm25，取 top-20
   │
   ├─ 3. RRF 融合（k=60）
   │
   ├─ 4. 交叉编码器重排（NVIDIA NIM）
   │
   └─ 5. 截断到 top-6，带 filename / chunk 序号 / 分数返回
```

**BM25 的分词器是自己写的，这是有原因的。** `rank_bm25` 默认按空白切词，对中文等于没切。引 `jieba` 又要多一个依赖和一部词典。所以这里用的是：拉丁词小写 + CJK 单字 + CJK 双字（bigram）。双字是中文检索精度的关键——只用单字的话几乎每篇文档都会命中。

**BM25 索引是进程内缓存，靠语料指纹失效。** 每次查询都从库里捞全部 chunk 建索引太慢；缓存又必须知道什么时候该失效。这里用 `(count, max(created_at))` 做指纹，比版本号简单，比不失效正确。

**重排失败会退回 RRF 顺序，不会让整个检索挂掉。** 交叉编码器是外部服务，会超时会被限流。降级之后答案质量下降，但用户仍然拿得到答案——这比返回 500 好。

**引用编号在重排之后才分配。** 否则模型引用的 `[1]` 和最终展示的顺序对不上。

## 四、事件协议

SSE 是唯一的下行通道。事件类型和字段：

| 事件 | 载荷 | 是否落库 |
|---|---|---|
| `run_started` | `agent` · `agent_name` · `tools[]` · `max_steps` | ✅ |
| `step` | `step` · `phase` · `status`(start/end) · `produced_tool_calls` | ✅ |
| `token` | `text` · `step` | ❌ |
| `tool_call` | `step` · `name` · `call_id` · `arguments` | ✅ |
| `tool_result` | `step` · `name` · `call_id` · `ok` · `duration_ms` · `preview` | ✅ |
| `citations` | `items[]` | ✅ |
| `usage` | `prompt_tokens` · `completion_tokens` · `model` | ✅ |
| `error` | `message` · `step` | ✅ |
| `run_finished` | `status` · `stopped_reason` · `steps` · `latency_ms` | ✅ |

每个事件都带 `seq`（运行内单调递增）。

**`step` 事件的 `produced_tool_calls` 字段是给前端做分组的。** 模型在调工具之前往往会先吐一段「我准备去查一下……」，这段文字和最终答案是混在同一个 token 流里的。没有这个标记，前端就没法把「思考过程」折叠起来、只突出最终答案。

**`tool_result` 里带 `call_id`。** 一轮里模型可能并发调好几个工具，靠名字匹配会串。

## 五、故障模型

免费层没有 worker，运行的宿主机就是 Web 进程本身，所以故障面就是进程本身。

**进程被杀 / 重新部署时会发生什么：**

1. 运行中的 `asyncio` 任务随进程消失
2. 数据库里那条 Run 还停在 `running`
3. 下次启动时 `recover_stale_runs()` 把它标成 `interrupted`，并写入原因

对账逻辑包在 `try/except` 里——**数据库不可达不能阻止进程启动**。免费层的数据库本身也会休眠，启动时连不上是常态，这时候应该降级启动并让 `/healthz` 如实报告，而不是直接崩掉。

**为什么订阅者不会永久挂起。** `EventBus.close()` 会往每个订阅队列里塞一个哨兵。这里有个容易漏的点：**队列满的时候塞哨兵会抛 `QueueFull`**，哨兵发不出去，那个订阅者就会永远等在一个已经结束的运行上。所以 `close()` 里会先腾位置。另外 `subscribe()` 里对「已关闭」的检查和队列注册之间**不能有 await**，否则存在这样的竞态：检查时还没关闭 → 注册前运行结束 → 哨兵发给了一个还没注册的队列。

**流式重试的边界。** 连接阶段失败会重试换 provider；**已经吐出过 token 之后再失败就绝不重试**——重试会让用户看到重复的文字。这个判断在 `stream()` 里是显式的。

## 六、安全

| 面 | 做法 |
|---|---|
| 密码 | bcrypt（12 轮），输入按 72 字节显式截断。不截断的话超过 72 字节的部分会被静默忽略，两个长密码只要前 72 字节相同就会互相通过 |
| 令牌 | JWT，`sub` = user_id，`tid` = tenant_id，默认 7 天 |
| 租户隔离 | 每个查询都带 `tenant_id` 过滤；跨租户访问返回 404 而不是 403（不泄漏资源是否存在） |
| 登录失败 | 邮箱不存在和密码错误返回**同一条**错误，不泄漏账号是否存在 |
| 工具调用 | Agent 只能调用 `tool_allowlist` 里声明的工具，白名单之外即使模型点名也会被拒 |
| 工具参数 | 每个工具的参数是 Pydantic 模型，模型返回的 JSON 先过校验。校验失败返回错误给模型让它自己改，不会抛异常打断循环 |
| 计算器 | 走 AST 白名单求值，**从不调用 `eval()`**；指数上限 64，防止 `2**999999999` 打满 CPU |
| 文件上传 | 扩展名白名单 + 25 MB 上限（**读 body 之前**先按声明的 `size` 拒绝，避免为注定被拒的文件付出内存）；`.pdf` / `.docx` 用 pypdf / python-docx 抽取正文，其余二进制格式（.doc/.xls/.ppt/图片…）明确拒绝 |
| 入库成本 | 单文档 chunk 上限（默认 10000，约 7.5 MB 英文正文 / 22 MB 中文），超限直接失败而不是截断。chunk 数决定嵌入调用数、行数、HNSW 体积与数据库占用 |
| 入库原子性 | 逐批 `flush()` 但只在最后 `commit()` 一次：内存峰值降到一批向量，而失败时不会留下半截可被检索到的索引（检索层不按文档状态过滤） |
| 渲染 | 前端先 HTML 转义再插标签，唯一的标签来源是我们自己，模型输出无法注入 |
| SQL | 全部走 SQLAlchemy 参数绑定，没有字符串拼接 |

**已知薄弱点：** 没有 Prompt 注入防护（用户可以在文档里埋指令影响模型行为），没有请求级限流，没有上传内容的沙箱。这三条都在 P3 清单里。

## 七、成本

`usage_ledger` 表按运行记录 `prompt_tokens` / `completion_tokens` / `latency_ms` / `cost_usd`。

NVIDIA NIM 的试用额度目前是免费的，所以 `MODEL_PRICES` 里都是 0；单价表是可配置的，换成付费 provider 时改环境变量即可，不用改代码。

**provider 返回 usage 时会用真实值；不返回时会退回到本地估算**（CJK 按 1 字 1 token，拉丁按 4 字符 1 token，再加 1 个 per-message 开销）。估算值只用于让账本不至于全是 0，注释里也写明了它**不用于计费**。

**并发是有闸的。** `llm_max_concurrency`（默认 4）用信号量限制同时发出的模型请求数。这不只是成本问题——512 MB 的实例上，几十个并发流式连接会把内存吃光。

## 八、数据库

八张表，都在 `migrations/versions/0001_initial_schema.py` 里：

| 表 | 作用 |
|---|---|
| `tenants` | 隔离边界 |
| `users` | 账号，每个账号注册时自动建一个租户 |
| `documents` | 上传的文档与索引状态 |
| `chunks` | 分块正文 + `vector(2048)` 嵌入 + HNSW 索引 |
| `runs` | 一次 Agent 运行的状态、结果、token、成本、耗时 |
| `run_events` | 已持久化的运行事件，用于重放 |
| `messages` | 会话消息（P1 的记忆功能会用到，目前还没写入） |
| `usage_ledger` | 用量流水 |

**`chunks.embedding` 的维度是写死在迁移里的（2048）**，不是从配置读的。迁移必须是不可变的：同一条 revision 无论什么时候重放都应该产生同样的 schema。要改维度就得写一条新的迁移去 `ALTER COLUMN`。

2048 这个数字来自 `nvidia/nemotron-3-embed-1b` 的模型卡，是核对过的——猜错的话 `INSERT` 会直接失败。

## 九、已知薄弱点

按严重程度排序：

1. **没有断点续跑。** 进程重启后运行被标记为中断而不是恢复。要真正续跑得引入 LangGraph 的 Postgres checkpointer。
2. **BM25 索引是进程内的。** 语料大了以后每次失效都要重建全量索引，内存也顶不住。上生产应该换成 Postgres 的 `tsvector` + GIN 索引。
3. **没有请求级限流。** 一个账号可以无限刷，会把免费额度耗光。
4. **前端没有 markdown 完整渲染。** 现在只支持粗体、行内代码、标题、换行——够用，但表格和代码块会退化成纯文本。

> 注：原 P1/P2 规划中的**「评测体系与黄金基准集」**（`app/eval`）、**「全链路 Span Tracing」**（`app/obs/tracing`）、**「多轮会话记忆」**（`messages` 表与 `thread_id` 上下文）以及**「多 Agent 模板（listing_optimizer）」**均已落地实现。

## 十、免费层的两条硬边界

这两条不是设计缺陷，是所选平台的规则，但会影响架构决策，所以记在这里。

**一、只有 750 实例小时。** Render 免费层给每个 workspace 每月 750 小时，而一个常驻服务一个月要吃掉约 720 小时。这就是为什么：

- 后端**只能有一个**常驻服务
- 前端必须是**静态站**——静态站没有 compute plan，不计入实例小时，也不休眠
- 任何"再起一个 worker 服务"的想法都行不通（免费层本来也不提供 worker 和 cron）

**二、服务发起的对外流量会被监控。** Render 免费层明确说明：*服务发起大量对外流量时可能被暂停*，原话举的例子是「访问外部数据库」和「调用外部 API」。本项目每次对话都要连 Neon、调 NVIDIA NIM，两条都命中。

这是这个架构里唯一一个"平台可能主动掐掉你"的风险，没有工程手段能绕开——只能控制用量，或者在真要做产品时上付费套餐。
